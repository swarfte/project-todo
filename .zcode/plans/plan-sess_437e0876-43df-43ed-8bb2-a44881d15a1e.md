# Plan: Move frontend `api.dart` logic into server-side `pb_hooks`

## Goal
Transform every data-operation method in `lib/api.dart` into custom PocketBase routes living in `server/pb_hooks/`, split into `project.pb.js`, `task.pb.js`, `step.pb.js`. **Frontend is NOT modified** (per request) — this only builds the backend API surface that a later frontend migration can target.

## API surface (verified against bundled `types.d.ts` for PocketBase **0.39.7**)

All routes use `routerAdd(method, path, handler, $apis.requireAuth())`. `$apis.requireAuth()` enforces a logged-in user (401 otherwise). Auth id = `e.auth.id`. The existing collection rules (`@request.auth.id = userId.id`, etc.) do NOT apply to server-side `$app.*` calls — so **every handler explicitly scopes queries by `e.auth.id`** to preserve the per-user isolation those rules enforce for the client.

## Implementation details

**1. Common patterns** (replicated per-file, no shared lib since JS hooks load files independently):
- Read path param: `e.request.pathValue("id")`
- Read body: `const body = e.requestInfo().body` (fields read via `body.name`, etc.)
- Read query: `e.requestInfo().query["projectId"]`
- Auth: `e.auth.id`
- Response: `e.json(200, record.publicExport())`; for lists, map `record.publicExport()`.
- Errors: `throw e.notFoundError(...)` / `e.badRequestError(...)`.

**2. Ownership scoping** — every query and every `findRecordById` is followed by an ownership check:
- `findRecordsByFilter("projects", "userId = {:uid}", "", 0, 0, { uid: e.auth.id })`
- For by-id operations, fetch then verify `record.getString("userId") === e.auth.id` (projects) or walk the relation for tasks/steps; return 404 if mismatch (avoid leaking existence).

**3. Atomic transactions** (user-chosen) — multi-write ops wrapped in `$app.runInTransaction((txApp) => {...})` using `txApp` for all writes:
- `duplicateTask`: deep-copy subtree + step chains; all-or-nothing. The project-`updatedAt` bump also runs inside the transaction.
- `insertStep`: create + re-link successor in one transaction.
- `deleteStep`: splice successor + delete atomically (fixes the current client's possible orphaned-head state).
- `unfinishAllSteps`: flip all completed steps to false in one transaction.

**4. Behavioral fidelity:**
- `createTask` bumps the parent project's `updatedAt` (re-save project name) exactly like the client, so the project page's ordering still works.
- `insertStep`/`deleteStep` reuse the linked-list splice logic (`previousStepId`) from the client, now transactional.
- `duplicateTask` names the root `"{name} copy"`, reuses the original's `previousTaskId`, and recursively copies children + steps preserving order/completion.

**5. No frontend changes** — `api.dart` stays as-is. These routes are additive.
